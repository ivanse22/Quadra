La regla práctica

/* La regla — si tienes dudas en un componente */

/* Por peso */
font-weight >= 700  →  font-family: var(--font-display)  /* Satoshi */
font-weight <= 600  →  font-family: var(--font-body)    /* DM Sans */

/* Por tamaño */
size >= --t-lg     →  Satoshi siempre
size <= --t-sm     →  DM Sans siempre
--t-base y --t-md →  depende del peso

/* Excepciones fijas */
inputs             →  DM Sans /* lo que escribe el usuario */
placeholders       →  DM Sans
nav items span     →  DM Sans --t-xs
currency-rate      →  DM Sans --t-xs /* tasa, secundaria */
CTAs / botones     →  Satoshi --t-md 700
Por que estos valores
--t-base bajó de 15px a 13px — DM Sans a 15px se percibía igual de grande que Satoshi a 17px. A 13px el body claramente se subordina al heading.
--t-hero subió de 48px a 56px — El número disponible es el momento más importante de la app. A 56px ocupa el ancho de pantalla con autoridad. La relación con el body (56 ÷ 13 = 4.3×) es clara.
--t-md como frontera de labels — A 15px en Satoshi 700, el label de campo se siente importante sin competir con los headings. DM Sans a 15px 400 se usaba antes — ahora ya no existe ese uso.
DM Sans solo en 400 y 500 — El 600 y 700 de DM Sans ya no se usan. Si necesitas peso, ya estás en territorio Satoshi. Esto elimina la zona gris.

18 · Estructura

Estados de pantalla

Toda pantalla puede estar en 4 estados: con contenido (documentado en secciones anteriores), cargando, vacía, o en error. Los tres estados especiales deben documentarse con el mismo rigor que el estado normal.

Empty states — pantallas sin contenido

Cada empty state tiene tres partes: visual (ícono o ilustración simple), headline que describe qué falta, y CTA claro que resuelve el vacío. El copy siempre es en primera persona y empático — no "No hay datos".

Reglas del copy — empty states
Headline — describe qué hay, no qué falta. "Aun no tienes pagos" en vez de "Sin pagos registrados"
Descripcion — explica el valor que se obtiene al resolver el vacío, no el proceso. Máximo 2 líneas
CTA — accion concreta, verbo en infinitivo. "Registrar mi primer pago", no "Nuevo pago"
CTA secundario — opcional. Solo si hay una accion educativa disponible ("Ver como funciona")
Tono — empático y directo. Nunca técnico. Nunca culpa al usuario
Cuando usar cada variante
Con hint box — cuando el vacío necesita contexto educativo. Ejemplo: Reservas con PILA, la primera vez que se ve
Con CTA doble — cuando hay una accion primaria y una educativa. Solo si la secundaria agrega valor real
Con icon de color semántico — Reservas usa fin-reserve, Pagos usa neutro. El color refuerza el contexto
Busqueda sin resultados — siempre con opcion de limpiar. Nunca sugerir "otros pagos" genéricos

Loading states — pantallas cargando

Dos niveles: skeleton completo de pantalla (primera carga o pull-to-refresh) y loading parcial inline (secciones individuales). Nunca spinner de pantalla completa — siempre skeleton que preserve el layout.

Preservar el layout — el skeleton debe tener exactamente la misma estructura visual que el contenido real. El usuario no debe ver un salto de layout al cargar

Primera carga de pantalla — skeleton completo que preserva estructura. Nav visible y funcional desde el inicio
Pull-to-refresh — skeleton solo en el área de contenido. Header y nav nunca se skeletan
Carga de sección — skeleton solo en esa sección. El resto de la pantalla sigue funcionando
Cálculo de disponible — pantalla dedicada con logo animado. Es un momento de transformación — merece su espacio

Reglas de aplicacion — para toda la app

Las 6 reglas del sistema
  • Entre > dentro — el espacio entre secciones siempre mayor que el espacio dentro. 32px entre secciones, 24px dentro de cards. Nunca al revés.
  • Horizontal constante — 20px de padding horizontal en toda la app, siempre. No 16px en unos componentes y 24px en otros.
  • Dividers para listas, gaps para secciones — las rows de lista se separan con 1px border, no con espacio. Las secciones se separan con 32px de gap, no con dividers.
  • El hero number no vive en una card — el número principal de cada pantalla va directamente sobre el fondo, sin contenedor. Su espacio es su jerarquía.
  • Bottom padding: 32px — el último elemento de cualquier pantalla scrolleable tiene 32px de espacio antes del nav o del borde. Nunca 0.
  • Row min-height: 48px — ninguna fila interactiva o informativa tiene menos de 48px de alto total. Es el mínimo para ser cómodo de leer y tocar.
Qué NO hacer
No usar gap uniforme — si todo usa --s5 (20px) de gap, el ojo no distingue agrupación. Varía por capa.
No anidar cards dentro de cards — genera doble padding y aumenta la densidad. Si un componente vive dentro de otro, usa una fila, no una card anidada.
No ignorar el bottom padding — el último elemento que toca el nav se siente cortado. Siempre 32px de buffer.
No variar el padding horizontal — 20px siempre. Si un elemento necesita más anchura, usa la pantalla completa (full-bleed), no 16px o 12px.
No poner más de 3 secciones sin respiro — si hay más de 3 bloques de contenido apilados, necesita un separador visual o espacio de 48px entre el tercero y el cuarto.
